# Scout / Outreach — операторский гайд

## Роли аккаунтов (важно)

| Тип | Что делает | ЛС |
|-----|------------|-----|
| **PARSER / OBSERVER** | Вступает в группы/каналы, парсит участников, скан keywords, пылесос постов | **Нет** |
| **OUTREACH / SENDER** | Только исходящие ЛС, отлежка, лимит **30–40/день** | **Да** |

Текущие CZ-фейки → **PARSER** (не пишут). Отдельные 1–3 акка с отлежкой → **SENDER**.

## Бан TG: что именно убито (не путать)

Официально ([core.telegram.org/api/errors](https://core.telegram.org/api/errors)) это разные вещи:

| Что видишь | Что мертво | Лечится сменой API_ID? | Что делать |
|---|---|---|---|
| `AUTH_KEY_DUPLICATED` | **Сессия** (auth_key). Аккаунт/номер живы | **Нет** — ключ уже инвалидирован сервером | Новый `tdata` / логин с одного IP+прокси |
| `SESSION_REVOKED` / `AUTH_KEY_UNREGISTERED` | Сессия отозвана | Нет | Новый логин |
| `FLOOD_WAIT_X` | Ничего — таймер | Нет | Спать X секунд, **не** крутить прокси |
| `PEER_FLOOD` | Софт-флаг «спам в ЛС» | Нет | Стоп ЛС 24–48ч → `@SpamBot` ≤4×/сутки |
| `USER_DEACTIVATED` / phone banned | **Номер/аккаунт** | Нет | Новый акк, старый номер мёртв |
| Прокси «не пускает» / timeout | IP прокси, не акк | Нет | Сменить прокси, сессию не трогать |

**Миф:** «переключусь на другой api_id/api_hash — сессия оживёт».
Не оживёт. `api_id` нужен только при создании сессии; сам `auth_key` хранится в `.session`.
Если ключ убит (`AUTH_KEY_DUPLICATED`) — нужен **новый логин**, не другой API.
Если номер в бане — любой API/клиент получит отказ.

Два «варианта», о которых ты помнишь, ближе к:

1. **Сломан вход/прокси** (сессия или IP) — аккаунт ещё жив.
2. **Забанен номер** (`PHONE_NUMBER_BANNED` / `USER_DEACTIVATED`) — аккаунт мёртв целиком.

## SpamBot

- Только **SENDER / OUTREACH** (парсеры/наблюдатели **не** пишут `/start` — им не зачем).
- Максимум **4 раза в сутки** на аккаунт (счётчик `spambot_today`, сброс в 00:05 MSK).
- На FLOOD у писателя: ротация прокси + SpamBot (если лимит не исчерпан).
- На `PEER_FLOOD` не дёргай SpamBot почаще — это ускоряет эскалацию до бана номера.

## Общий пул групп

Таблицы `scout_target_chats` + `scout_chat_memberships`.

1. Админка → ЦА → вставь список → **«В пул + очередь»** (не join сразу).
2. Воркер раз в **~30 сек** берёт **один** PENDING и делает join.
3. Новый PARSER/OBSERVER → кнопка **«В пул групп»** или авто при создании карточки — подхватывает весь ACTIVE-пул.
4. Сгорел наблюдатель → список **не** теряется; новый акк просто enroll.

## Отказоустойчивость (что переживает сгорание акка)

| Слой | Где лежит | Если акк сгорел |
|---|---|---|
| Список групп | `scout_target_chats` | **остаётся** |
| Очередь join | `scout_chat_memberships` | снимается с мёртвого → **handoff** живому |
| Телефон / User ID / DC / заметка покупки | `accounts.json` + карточка | **остаётся** (даже без сессии) |
| Проспекты / лиды / шаблоны | Postgres/H2 | **остаются** (привязка к scout_id — метка, не единственная копия) |
| Логи действий | `scout_action_log` | **остаются** |
| Сессия TG / ЛС внутри акка | `.session` + сервера TG | **мертвы** — не бэкапятся (нужен новый tdata) |
| «Уже вступил в группу в TG» | факт на стороне Telegram | новый акк **join'ит заново** по тому же пулу |

Кнопки:
- **В мёртвые** (PARSER/OBSERVER) → статус BURNED + авто-failover на первого живого watch-скаута
- **Перенести пул** → явный handoff (можно указать ID получателя)
- Новый скаут → **В пул групп** / авто при создании

Правило: знание в Pulse, доступ в Telegram. Сгорел доступ — знание не трогаем, доступ поднимаем на другом акке.

## Почему аккаунты «сгорают» (главная причина потерь)

Telegram убивает `auth_key` навсегда, если **один и тот же ключ** подключается
с двух IP одновременно (`AuthKeyDuplicatedError`). Восстановлению не подлежит:
ни старый `tdata`, ни `authKey` из `accounts.secrets.json` больше не сработают —
нужен новый `tdata.zip` на тот же номер.

Как ключ дублируется на практике:

- один `tdata.zip` залили **двум разным скаутам** в админке → две `.session` с одним ключом;
- файл `.session` скопировали руками (`observer-1.session` ← копия `outreach-1.session`);
- параллельно с sidecar тот же номер открыт в **Telegram Desktop / телефоне через другой IP**;
- скаут ходил то через прокси, то напрямую.

Правила, которые это исключают:

1. **1 купленный аккаунт = 1 скаут = 1 `.session` = 1 прокси.** Никогда не заливай один
   `tdata` в два слота — заведи второй аккаунт.
2. После заливки `tdata` **закрой Desktop** на этом номере и больше его не открывай.
3. Прокси назначай **до** первого коннекта и не меняй без причины.

Контроль в админке (вкладка **Скауты**):

- красная плашка **«Один ключ в нескольких сессиях»** — список конфликтов, чинить сразу;
- бейдж **«дубль ключа»** в строке скаута;
- бейдж **«ключ мёртв»** + статус **Сгорел** — ключ уже убит, нужен новый `tdata`;
- фильтр **Рабочие / Сгоревшие / Все**, кнопки **В мёртвые**, **Сбросить сессию**, **Удалить**;
- **бесхозные `.session`** (не привязаны ни к одному скауту) удаляются кнопкой из той же плашки.

Локальная проверка без сети (ключи не сгорят):

```bash
python scripts/audit_sessions_cli.py
```

Печатает отпечаток `auth_key` каждой сессии и группы дублей.

Что делать, если скаут сгорел:

1. **Сбросить сессию** — карточка, телефон, User ID и заметка о покупке остаются.
2. Взять на тот же номер новый `tdata.zip` (в магазине это перевыдача, не новая покупка).
3. Залить в того же скаута → статус вернётся в **Прогрев**.
4. Если номер не отдают — **Удалить** скаута и завести нового на свежий аккаунт.

## Прокси

1. Админка → **Прокси**: вставь список / перетащи `.txt` / кнопка «Выбрать .txt»
2. Форматы (оба ок):
   - `ip:port:user:password`
   - `user:password@ip:port`
3. **Проверить живые** — TCP на порт (отсекает дохлые). Потом **Дать прокси** на скауте.
4. Правило: **1 прокси = 1 аккаунт**, sticky. Ротация только при FLOOD/бане — иначе ТГ палит «скачущий IP».
5. Опционально: `data/proxies-inbox.txt` подхватывается сам (~15 сек).

При **FLOOD / PEER_FLOOD / BAN**:
- текущий прокси → invalid
- назначается следующий свободный
- `/start` @SpamBot
- мёртвые чистятся кнопкой «Убрать мёртвые»

## Добавить SENDER-аккаунт

1. `accounts.json` — новый id, `"type": "SENDER"` или `"OUTREACH"`
2. Логин: `python scripts/login.py 3` или `.session` файл
3. В БД `scout_accounts`: label, type=OUTREACH, daily_limit=35, status=ACTIVE (или WARMING пока греешь)
4. Assign proxy: `/admin/proxies` или API `POST /v1/proxy/assign`

## Парсеры

- Join: `POST /v1/chat/join` · **массовый импорт в админке:** вкладка **Чаты** (textarea или `.txt`)
- Members: `POST /v1/group/members` (бот: Парсить группу)
- Vacuum контента: `POST /v1/chat/vacuum`
- Radar scan: observer worker раз в час

Импорт ссылок: `/admin/` → Чаты → вставь `t.me/…` / `@username` по строке → «Вступить». Идёт на PARSER/OBSERVER.

## Рассылка + ИИ

При старте кампании LLM пишет **крючок ≤14 слов** + шаблон с `{username}` / `{channel}` / `{topic}`.

Тест «1 ЛС»:
1. Нужен **SENDER** аккаунт + proxy
2. Кампания → свой @username → Запустить
3. Лог `DM_SEND` в боте / `/admin/logs`

## Антибан sender

- daily_limit 30–40 (жёсткий потолок 40 в коде)
- пауза 45–120 сек между ЛС
- FLOOD → proxy rotate + SpamBot → статус ACTIVE если бот ответил ок

## Админки

- Бот: Pulse Ассистент → Скауты (admin)
- Веб: `http://127.0.0.1:8081/admin/?token=...`
  - **Обзор** — sidecar, SENDER, очередь ЛС, прокси
  - **Прокси** — пул в `scout-sidecar/proxies.json` (не в Postgres): живые / в работе / запас / мёртвые
  - **Скауты** — список + создать карточку + профиль TG; сессия (tdata/.session) пока через sidecar
  - **Переписка** — диалоги, ответ, «прочитано» только по кнопке
  - **ЦА / парсинг** — скор участников (hot/warm vs мёртвые)
- JSON API: `/admin/api/*`
